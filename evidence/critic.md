# Критик — замечания к черновику REVIEW.md (01.11.2026)

Проверено сопоставлением каждого числа в REVIEW.md §1–6 с записями `evidence/*.md`, плюс чтение кода
(`app/mailing/engine.py:296–326`, `app/lead_parser.py:45, 809, 996`, `app/desktop_services.py:131`) и `git status`.
Файлы, кроме этого, не менялись. Формат: `K-NN · утверждение · проблема · доказательство · рекомендация`.

## Вердикт и правила

**K-01 · «Блокеров для такого использования нет» (§1, §4)**
Проблема: рассылка входит в «работу продукта» (паспорт §2: «написать в Telegram (вручную или пачкой)»). Часть дефектов
рассылки — не ошибка владельца, а штатный ход событий: ответ после создания повтора → напоминание всё равно уходит
(E-M-11); «СТОП», пришедший при закрытом приложении **или когда нет идущей кампании**, теряется → повтор пишет
отказавшемуся (E-M-14); зависшее `sending` уходит мимо стоп-листа (E-M-07). Это повторные сообщения людям, явно
отказавшимся, — вред третьим лицам и прямой правовой риск (152-ФЗ, отзыв согласия; E-M-19). По правилу «main scenario
fails» сценарий «пачка → повтор» сейчас проваливается. В §1 это подано как условие перехода к No-Go («если рассылка
запущена…»), а должно быть частью самого вердикта.
Рекомендация: вердикт явно делить по сценариям; живую пакетную рассылку и повторы объявить **No-Go до исправления
E-M-07/08/10/11/13/14** — как условие Conditional Go, а не как «риск».

**K-02 · Сужение вердикта до «собственной работы владельца» (§1)**
Проблема: само сужение законно — паспорт называет пользователем владельца-одиночку. Но паспорт же указывает канал
«zip для других людей», а правило No-Go «cannot install/run for a new user» тогда нужно оценить явно, а не обойти.
Доказательств «не ставится у нового человека» нет: E-U-02 — чистый exe на пустом DATA_DIR запустился за 3,4 с (на
машине владельца, где есть Chrome и WebView2); чистая машина, SmartScreen, отсутствие Chrome — не проверены (F-O-02…04,
§7). Значит, для передачи другим верный статус — «не проверено → не готово», а не скрытое умолчание.
Рекомендация: дать вторую строку вердикта: «Передача другим людям — No-Go до проверки на чистой Windows (неподписанный
exe, установщик не собирался)». Тогда сужение — не уловка.

**K-03 · «Главный сценарий … написать → поставить статус проходит» (§1)**
Проблема: шаги «написать» и «статус» вживую ни разу не пройдены: 0 отправленных, 0 смен статуса за 17 дней (E-V-02,
E-V-03, E-V-05); открытие Telegram по «Написать» и автоотметка «Отправил» не проверены (E-U «Не проверено»);
E-U-06 — синтетика и только копирование в буфер. «Перезапуск ничего не теряет» (E-S-10) — на подменённом
`request_page`, не на живом поиске. Правило Go требует «main scenarios pass with evidence».
Рекомендация: «Поиск проверен вживую (2 прогона, 15 карточек, один город); шаги «написать/статус» проверены на
синтетике, у владельца ни разу не выполнены».

## Числа и утверждения, не совпадающие с доказательствами

**K-04 · «секреты … нигде не утекают» (§1), «0 утечек … в публичном GitHub» (§3 E)**
Проблема: E-O-04 — в публичном зеркале сканер дал **findings = 3** (публичный ник владельца `owner-test-recipient`
в `app/script_texts.py` и 2 документах). E-M-15 — `mailing.sqlite3` не шифруется: username, телефоны, тексты, access_hash
открытым текстом; копия папки (robocopy) теряет ACL. E-O-06 — сканер слеп к сжатому PYZ, «0 в dist» ограничено.
E-O-09 — тексты отзывов частных лиц уходят в OpenRouter, приложение советует включить «training».
Рекомендация: «Ключи и сессии зашифрованы DPAPI; в логах/сборке/zip ключей не найдено (со слепой зоной PYZ); в
публичном репозитории — только ник владельца (3 места); база рассылки с контактами третьих лиц — без шифрования».

**K-05 · «нужен Chrome без предупреждения» как факт (§1, §3 F, R8)**
Проблема: основной поиск — HTTP (`run_search_http`, E-S-01; живые прогоны E-S-03/04 прошли без браузера). Chrome нужен
для отката `run_search_browser`, «Обновить карточку» (`desktop_services.py:131`) и «Медиа» (`desktop_gallery.py`).
F-O-04 сам пишет «поведение без Chrome не проверено». E-S-01 и F-O-04 противоречат друг другу («поиск через Chrome»).
Рекомендация: «Без Chrome не работают откат поиска, обновление карточки и медиа; понятного сообщения нет; на чистой
машине не проверено».

**K-06 · «≈ 450 сообщений/мес» и модель «сделки = 450 × r × c» (§5)**
Проблема: (а) дневной лимит считает **все** живые попытки аккаунта (`engine.py:306–307`: `attempts … status IN
('sent','sending')`), включая напоминания. При «первое + 1 напоминание» первых сообщений ≈ 225/мес → сделок вдвое меньше.
(б) 450 адресатов с Telegram в месяц требуют лидов: у владельца 82 за 17 дней, видимых 42 (40 скрыты, E-V-01), ссылка
на Telegram у 19 из 42 (45 %), резолв телефон→Telegram — 0 раз (E-V-07). Узкое место — поток лидов, а не лимит.
(в) «5 в первый день, +3/день» — E-V-13 считает 450–500 «по коду, не наблюдение» — в §5 это стоит в «Наблюдалось».
Рекомендация: N = min(лимит, лиды с Telegram); показать вариант N ≈ 200; перенести лимиты в «допущения/расчёт».

## Оценки

**K-08 · Оценки смешивают два масштаба вердикта**
Проблема: вердикт — «поиск + ручная переписка», а B, D, E оценены вместе с рассылкой. E = 2 при том, что отказ «СТОП»
надёжно не соблюдается (E-M-07, E-M-14), база контактов без шифрования (E-M-15), нет CSP при 55 `innerHTML` (E-O-10),
карантин снимается одной кнопкой (E-M-19) — для рассылки это 1. D = 2 для поиска обосновано, но с рассылкой
(гонки E-M-08/09, потеря ответов E-M-14, зависание до ~65 с при закрытии E-S-16) — 1.
C «средне-высокая» уверенность — только синтетика, одно разрешение, без масштаба 125–150 % → «средняя».
Рекомендация: давать B/D/E по двум строкам (поиск / рассылка) или явно оценить в рамках вердикта: E = 2 (поиск+ручная),
1 (рассылка); D = 2 / 1.

## Пропущено или недооценено

**K-09 · Потеря данных рассылки не в таблице рисков**
F-O-07/F-O-08: `mailing.sqlite3` мигрирует ALTER TABLE без бэкапа, нет проверки «база новее», ручной бэкап её не
копирует. Потеря стоп-листа = повторные сообщения отказавшимся; «данные: потеря/порча» — критерий No-Go. В REVIEW это
только в линзе F и в п. 6 дорожной карты («передача другим»), хотя касается владельца при каждом обновлении папкой.
Рекомендация: отдельный риск R в §4 (серьёзность высокая), в дорожную карту — пунктом 1 вместе с дублями.
