# Решения по модулю рассылки

Формат: решение — альтернативы — причина — источник.

## D0. Где лежат документы и база кода

- **Решение.** Документы модуля — в `docs/mailing/` (`AUDIT.md`, `DECISIONS.md`, `KNOWN_ISSUES.md`, `ACCEPTANCE.md`). Код — в пакете `app/mailing/`. Ветка начата со снимка незакоммиченного продукта из основной папки (коммит `15fae87`).
- **Альтернативы.** Файлы в корне (там уже есть чужой `AUDIT.md` на 74 КБ); работа от `b0991c9` без снимка.
- **Причина.** Не смешивать с прежними отчётами; строить на том продукте, который реально собран в `dist`.
- **Источник.** `git -C parserYand status` (32 изменённых файла от 2026-10-17), `docs/mailing/AUDIT.md` §0.

## D1. Mini App или Desktop — **Desktop**

| Критерий | Desktop (pywebview, локальный процесс) | Mini App (страница в клиенте Telegram + сервер) |
|---|---|---|
| Где живёт сессия | В том же процессе, что Telethon; файл на ПК владельца | Страница не имеет доступа к MTProto-сессии пользователя, она «can't … send new ones on behalf of the user» ([webapps](https://core.telegram.org/bots/webapps)). Значит, Telethon и сессии должны жить на сервере (`77.239.101.211`, Docker) |
| Безопасность | Сессия шифруется DPAPI ключом пользователя Windows, папка доступна только ему. Внешнего хостинга нет | Полный доступ к аккаунтам лежит на внешнем сервере; утечка сервера = утечка всех аккаунтов. Нужны защита сервера, бэкапы ключей, отдельный секрет шифрования |
| Распространение | Zip с portable-папкой и ярлыком уже собирается (`build.ps1`, `create_shortcut.ps1`). Каждый вводит **свои** `api_id/api_hash` — требование «You must obtain your own api_id» ([terms 2.1](https://core.telegram.org/api/terms)) выполняется само | Другому человеку нужен свой сервер, бот, домен и HTTPS — «без кода и команд» невозможно; общий сервер означал бы чужие ключи и сессии у владельца |
| Надёжность | Кампания идёт, пока открыто окно; после закрытия и запуска продолжается с того же места (состояние в SQLite) | Сервер работает круглосуточно — плюс. Но паузы и FloodWait одинаково решаются логикой ядра, а не местом |
| UX | Вход и управление в том же окне, где база; уже есть общая кнопка «← Назад» (`stage9.js:22-31`) | Ввод кода и 2FA в Mini App отправляет код на сервер — лишний переход секретов через сеть |
| Тестируемость | Ядро без UI, `FakeGateway`, unittest; мост проверяется без окна | То же ядро плюс HTTP-слой, авторизация `initData`, деплой |

**Итог.** Модуль живёт в Desktop. Главная причина: MTProto-сессия даёт полный доступ к аккаунту, а Mini App не может её держать — пришлось бы хранить сессии всех аккаунтов на внешнем сервере. В Desktop сессия не покидает ПК владельца и зашифрована его учётной записью Windows, а zip для других людей содержит только программу: каждый вводит свои ключи. Длительность кампании ограничена временем работы окна — это компенсируется продолжением после перезапуска (A6). Mini App (`app/api.py`, `app/static/*`, репозиторий `lead-mini-app`) **не трогаем вообще**: ни панели просмотра, ни копии `miniapp_mailing/` не делаем — для неё нужен был бы сервер со статистикой, а это отдельная задача без пользы для приёмки.

## D2. Хранение состояния

- **Решение.** Отдельный файл `%APPDATA%\LeadEqualMoney\mailing\mailing.sqlite3` (WAL). Организации читаются из `app.sqlite3` только на чтение; старая база и её схема не меняются.
- **Альтернативы.** Новые таблицы в `app.sqlite3`; старые таблицы `campaigns/campaign_recipients`.
- **Причина.** Требование «не меняй старую базу»; старые таблицы рассчитаны на один аккаунт и обязательное согласие каждого адресата.
- **Источник.** `app/db.py:148-185`.

## D3. Библиотека MTProto — Telethon 1.45.0 (закреплена)

- **Альтернативы.** Pyrogram 2.0.106 (последний выпуск 2023-04-30 — заброшен), Kurigram 2.2.26 (форк Pyrogram, 2026-09-12).
- **Причина.** Уже закреплена в `requirements-exe-lock.txt` и включена в сборку (`packaging/LeadEqualMoney-onedir.spec:21`), последний выпуск 2026-09-10, репозиторий активен (codeberg, 5 открытых задач на 2026-10-30). Новых зависимостей не добавляем.
- **Источник.** PyPI JSON API `pypi.org/pypi/telethon/json`, `codeberg.org/api/v1/repos/Lonami/Telethon`, `telethon/version.py`.
- Коды ошибок проверены в установленном `telethon/errors/rpcerrorlist.py`: `FloodWaitError` (`seconds`), `PeerFloodError` («account is limited (spam-reported)… retrying will not help»), `UserPrivacyRestrictedError`, `UserDeactivatedBanError`, `AuthKeyUnregisteredError`, `SessionRevokedError`, `FrozenMethodInvalidError`, `UserIsBlockedError`, `UsernameNotOccupiedError`. Ошибок `PRIVACY_PREMIUM_REQUIRED` и `ALLOW_PAYMENT_REQUIRED` в 1.45.0 нет отдельными классами — распознаются по тексту `RPCError.message` (**не проверено на живом сервере**).

## D4. Сессии и ключи

- **Решение.** `StringSession` Telethon, зашифрованная Windows DPAPI (`CryptProtectData`, область текущего пользователя) с дополнительной энтропией модуля. Файлы `mailing\keys.bin` (`api_id`, `api_hash`) и `mailing\accounts\<id>.bin` (сессия, телефон). Права на папку `mailing\` сужаются `icacls` до текущего пользователя (наследование отключено).
- **Альтернативы.** Обычный файл `.session` (как в `telegram_sender.py` — без шифрования); Windows Credential Manager (ограничение размера ~2.5 КБ на запись, сессия больше).
- **Причина.** DPAPI уже применяется в проекте (`app/telegram_sender.py:79-128`), не требует пароля и новых пакетов; расшифровать может только тот же пользователь Windows.
- **Источник.** learn.microsoft.com — CryptProtectData; Telethon `sessions/string.py`.
- Импорт ключей владельца: кнопка «Загрузить из файла» читает `secrets\accounts.json` через диалог и сразу шифрует значения. Файл не копируется.

## D5. Как найти получателя — **username из соцсетей организации**

| Способ | Риск для аккаунта | Надёжность | Приватность |
|---|---|---|---|
| Username из ссылки `t.me/<name>` в карточке | Низкий: один `contacts.resolveUsername` на адресата, результат кешируется | Только публичные username; ссылка может вести на канал или бота — такие пропускаются | Организация сама опубликовала ссылку |
| Номер через импорт контакта (`contacts.importContacts`) | Высокий: массовый импорт незнакомых номеров — признак спама; засоряет контакты; в `telegram_sender.py` уже нужна ручная очистка | Зависит от настроек видимости номера | Номер уходит в Telegram как «контакт» владельца |
| Ссылка `t.me/+<номер>` | Через API не разрешается без импорта контакта; это ручной путь | — | — |

- **Решение.** Отправка только по username. Номера используются лишь для дедупликации и как подсказка «можно написать вручную» (существующая кнопка «Проверить ТГ»). Импорт контактов в модуле не реализован.
- **Источник.** core.telegram.org/method/contacts.resolveUsername, /method/contacts.importContacts; `app/telegram_sender.py:295-355`; счётчики базы в `AUDIT.md` §2.

## D6. Идемпотентность отправки

- **Решение.** Перед сетевым вызовом в БД фиксируется попытка со статусом `sending` и постоянным `random_id`. Отправка идёт через `messages.SendMessage` с этим `random_id`. При перезапуске попытка в `sending` сверяется: сначала по истории диалога (последние сообщения от нас после времени попытки), затем повтором с тем же `random_id` — сервер отвечает `RANDOM_ID_DUPLICATE`, если сообщение уже было.
- **Причина.** `random_id` — «Unique client message ID required to prevent message resending» ([sendMessage](https://core.telegram.org/method/messages.sendMessage)). Срок, в течение которого сервер помнит `random_id`, в документации не указан — **не проверено**, поэтому первым идёт сверка по истории.

## D7. Значения правил безопасности по умолчанию (меняются в «Настройках рассылки»)

| Правило | По умолчанию | Границы |
|---|---|---|
| Лимит нового аккаунта, 1-й день отправки | 5 | 1–50 |
| Прирост лимита в день | +3 | 0–10 |
| Потолок лимита в день | 25 | 1–50 |
| Не больше в час | 8 | 1–30 |
| Пауза между сообщениями одного аккаунта | случайно 90–240 с | минимум 45 с |
| Окно отправки по времени получателя | 10:00–19:00, пн–пт | — |
| FloodWait ≤ 300 с | ждать столько, сколько сказал сервер (+случайно 5–30 с), затем одна попытка | — |
| FloodWait > 300 с | аккаунт на паузу до конца суток или до конца ожидания, если позже | — |
| PeerFlood, бан, деактивация, отзыв сессии, «заморозка» | аккаунт в карантин, его кампания остановлена, событие в журнал | снимается только вручную |
| Приватность, блокировка, нет такого username, канал/бот | адресат помечен «недоступен», повторов нет ни в одной кампании | — |
| Часовой пояс получателя | по городу из `business_tags` (таблица крупных городов), иначе Москва | — |

- **Причина.** Telegram прямо предупреждает о вечном бане за флуд и спам и о том, что аккаунты неофициальных клиентов «automatically put under observation» ([obtaining_api_id](https://core.telegram.org/api/obtaining_api_id)). Значения консервативные и взяты с запасом относительно старого кода (`telegram_sender.py`: 5 в день, 60 с). Точных официальных лимитов Telegram не публикует — **не проверено**.
- При карантине трафик на другие аккаунты **не переключается**: получатели закреплены за аккаунтом при создании кампании, и кампания останавливается целиком.

## D8. Тестовый контур

- Аккаунт с `is_test: true` может отправлять **только** адресатам из `secrets\accounts.local.json → test_recipients` (проверка в ядре перед каждой отправкой). Тестовая кампания берёт тексты из реальных карточек, но доставляет их тестовым адресатам.
- Новая кампания всегда создаётся в режиме «сухой запуск». Реальная отправка включается отдельной кнопкой с вводом слова `ОТПРАВИТЬ`.

## D9. Подсказки скриптов

- **Решение.** Используются существующие `db.templates()`, `FIRST_BY_SITE_TYPE` и `render_template` из parserYand. Таксономия `lead-mini-app` не переносится.
- **Причина.** Требование переиспользовать; перенос таксономии — отдельная задача и изменение старой базы шаблонов. Поля в квадратных скобках (`[имя]`) блокируют запуск, пока их не заменят.
- **Источник.** `app/script_templates.py:60-64`, `app/desktop.py:375-387`.

## D10. Ответы получателей

- **Решение.** Простой обработчик входящих Telethon (`events.NewMessage(incoming=True)`) работает, пока аккаунт подключён для кампании: ответ от адресата кампании записывается как «ответил», текст «стоп / не пишите / отпишите» — в стоп-лист. Ответы, пришедшие при закрытом приложении, не учитываются. CRM-статус в старой базе модуль не меняет.

## D11. Сборка: обновления безопасности и часовые пояса

- **Решение.** В `requirements-exe-lock.txt` подняты `certifi` 2026.7.22 → 2026.10.18 (GHSA-6q48-6c7w-9gw2) и `setuptools` 84.0.0 → 84.1.0 (GHSA-xmj3-9gf7-h52w); в `requirements-lock.txt` — `certifi`. В onedir-спеку добавлены данные `tzdata` и подмодули `app.mailing`. Новых пакетов нет.
- **Причина.** Уязвимости найдены по базе OSV на этапе 1; исправленные версии есть на PyPI. `zoneinfo` в Windows без `tzdata` не знает часовых поясов, а окно отправки считается по городу получателя.
- **Источник.** api.osv.dev; `scripts/mailing_osv_audit.py` после изменения: 0 уязвимых пакетов из 48.

## D12. Проверка «чистой машины» через порт DevTools WebView2

- **Решение.** `scripts/mailing_clean_machine.py` запускает собранный `LeadEqualMoney.exe` с переменной `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=…` и пустым `DATA_DIR`. Переменная задаётся только в тесте; в приложении и ярлыке её нет.
- **Альтернативы.** UI Automation (нужен новый пакет), ручная проверка.
- **Причина.** Позволяет пройти мастер в настоящем exe без терминала и без новых зависимостей.

## D13. Zip для других людей

- **Решение.** `scripts/mailing_make_zip.py` упаковывает `dist\LeadEqualMoney`, `create_shortcut.ps1`, «Создать ярлык.cmd» (двойной щелчок) и «ПРОЧТИ.txt». Перед упаковкой отклоняет файлы `secrets`, `.env`, `.session`, `keys.bin`, базы рассылки; после упаковки zip сканируется `scripts/mailing_leak_scan.py` с точными значениями из файла владельца.
